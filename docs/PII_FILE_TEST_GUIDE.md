# 개인정보 탐지 첨부파일 테스트 가이드

## 목적

이 문서는 `POST /pii/detect/file`로 첨부파일을 업로드해 개인정보 탐지 결과를 확인할 때 사용하는 검증 문서이다.

기존 검증용 문서 `개인정보탐지_테스트 (1).docx`의 샘플을 기준으로, 사용자가 결과를 쉽게 판단할 수 있도록 다음 기준으로 정리했다.

- 탐지되어야 하는 케이스
- 구조상 탐지되지 않아야 하는 케이스
- 현재 구현에서 오탐/중첩 탐지 여부를 확인해야 하는 케이스
- 기본 룰셋에서는 제외되어 오해하기 쉬운 케이스
- 문맥 필터 때문에 결과가 달라질 수 있는 케이스
- 표 형태처럼 개별 셀에는 문맥 라벨이 없어도 반복 행/헤더로 탐지되는 케이스

## 테스트 전 확인

기본 룰셋은 `default`이다.

```bash
curl http://localhost:8005/pii/rulesets
```

DOCX 첨부파일 업로드 테스트:

```bash
curl -X POST "http://localhost:8005/pii/detect/file" \
  -F "file=@docs/PII_FILE_TEST_SAMPLE_CONTEXT.docx" \
  -F "max_results_per_type=500"
```

TXT 샘플로 본문만 빠르게 확인:

```bash
curl -X POST "http://localhost:8005/pii/detect/file" \
  -F "file=@docs/PII_FILE_TEST_SAMPLE.txt" \
  -F "max_results_per_type=500"
```

텍스트 직접 테스트:

```bash
curl -X POST "http://localhost:8005/pii/detect" \
  -H "Content-Type: application/json" \
  -d '{"text":"주민등록번호: 890512-2054508 / 이메일: test.user+aa@company.co.kr / 연락처: 010-5555-6666"}'
```

## 베트남 PII 테스트 상세

베트남 PII는 기본 룰셋에서 다음 응답 키로 반환된다.

| 응답 키 | 의미 | 대표 라벨 | 대표 형식 |
| --- | --- | --- | --- |
| `VN_CCCD` | 베트남 시민신분증/개인식별번호 | `CCCD`, `căn cước công dân`, `베트남 신분증` | 성/시 코드 prefix + 12자리 |
| `VN_MN` | 베트남 휴대폰번호 | `số điện thoại`, `sdt`, `베트남 휴대폰` | `0981234567`, `098-123-4567` |
| `VN_PN` | 베트남 여권번호 | `hộ chiếu`, `passport`, `베트남 여권번호` | 영문 1자리 + 숫자 8자리 |
| `VN_TIN` | 베트남 세금번호/납세자번호 | `mã số thuế`, `tax code`, `베트남 세금번호` | 10자리 또는 `10자리-3자리` |
| `VN_SI` | 베트남 사회보험/건강보험 코드 | `mã số BHXH`, `BHYT`, `베트남 사회보험번호` | 10자리 |

테스트 샘플 파일:

- `examples/vietnam_pii_true_positive_sample.json`: 탐지 위주 단일 샘플
- `examples/vietnam_pii_mixed_cases.json`: 탐지/미탐/표/경계값 혼합 샘플
- `examples/vietnam_pii_mixed_cases.txt`: 사람이 복사해 넣기 쉬운 텍스트 샘플

### 탐지되는 베트남어/무성조/한국어 라벨

베트남어 성조가 있는 라벨과 성조가 제거된 라벨 모두 문맥 라벨로 사용할 수 있다.

```text
Số căn cước công dân: 079213456789
Số điện thoại: 0981234567
Số hộ chiếu: B12345678
Mã số thuế: 0312345678
Mã số BHXH: 7938922623
```

```text
so CCCD 001199123456
so dien thoai 032-123-4567
ho chieu C87654321
ma so thue 0101243150-001
ma the BHYT 0123456789
```

한국어 라벨도 베트남 타입 문맥으로 인정된다.

```text
베트남 신분증: 024188654321
베트남 휴대폰: 091 234 5678
베트남 여권번호: D11223344
베트남 세금번호: 0312345678-001
베트남 사회보험번호: 1234567890
```

### 표 형태 입력과 헤더 라벨

아래와 같은 줄은 한 줄만 테스트하라는 의미가 아니다. 엑셀, CSV, Word 표, 웹 표를 복사했을 때 나오는 “헤더 + 데이터 행” 구조를 테스트하기 위한 샘플이다.

```text
Ho ten | CCCD | So dien thoai | Ho chieu | MST | BHXH
Nguyen Van A | 079200987654 | 0887654321 | S11223344 | 0312345678 | 7938922623
Tran Thi B | 001188123456 | 097-111-2222 | B99887766 | 0101243150-001 | 0123456789
```

현재 기본 정책에서는 위 표에서 `VN_CCCD`, `VN_MN`, `VN_PN`은 탐지될 수 있다. 반면 `VN_TIN`, `VN_SI`는 미탐이 정상이다.

이유는 `VN_TIN`, `VN_SI`가 모두 10자리 숫자 중심 형식이라 주문번호, 티켓번호, 내부 관리번호와 충돌하기 쉽기 때문이다. 따라서 현재 룰은 표 헤더만으로 `MST`, `BHXH` 열 값을 통과시키지 않고, 값 가까이에 라벨이 있는 경우를 중심으로 통과시킨다.

탐지되는 형태:

```text
ma so thue: 0312345678
ma so BHXH: 7938922623
베트남 세금번호: 0312345678-001
베트남 사회보험번호: 1234567890
```

미탐이 정상인 표 헤더 형태:

```text
이름 | 베트남 세금번호 | 베트남 사회보험번호
Nguyen Van A | 0312345678 | 7938922623
```

### 한국 PII 표 탐지와의 차이

기본 문맥 설정에서는 한국 PII 타입의 표 헤더 문맥이 활성화되어 있다.

```yaml
table_header_enabled: true
table_header_line_fallback: true
```

따라서 아래와 같은 한국 PII 표는 헤더 문맥으로 탐지될 가능성이 있다.

```text
이름 | 휴대폰번호 | 여권번호 | 사업자등록번호
홍길동 | 010-1234-5678 | M12345678 | 220-81-62517
```

반면 베트남 `VN_TIN`, `VN_SI`는 타입별 설정에서 표 헤더 기반 통과를 꺼둔다.

```yaml
VN_TIN:
  table_header_enabled: false

VN_SI:
  table_header_enabled: false
```

정리하면 다음과 같다.

| 구분 | 표 헤더 기반 탐지 기대 |
| --- | --- |
| 한국 PII `SN`, `MN`, `PN`, `BRN`, `BN`, `CN` 등 | 탐지 가능 |
| 베트남 `VN_CCCD`, `VN_MN`, `VN_PN` | 탐지 가능 |
| 베트남 `VN_TIN`, `VN_SI` | 표 헤더만으로는 미탐이 정상 |

운영 정책상 `MST`, `BHXH` 표 컬럼도 탐지해야 한다면 `VN_TIN`, `VN_SI`의 `table_header_enabled` 정책을 별도로 조정해야 한다.

| 베트남 라벨 없는 숫자 | `Ma don hang 079213456789, serial 0981234567` | 베트남 타입 미탐 | PII 문맥 없이 숫자/코드처럼만 존재 |

## 오탐/중첩 탐지 확인 케이스

아래 항목은 사람이 보기에는 무효이거나 다른 번호 유형에 가까우나, 현재 pipeline에서는 일부 타입으로 잡힐 수 있다. 이 구간은 “미탐 성공”이 아니라 오탐 또는 중첩 탐지 여부를 확인하는 용도이다.

| 구분 | 테스트 문자열 | 확인할 응답 | 해석 |
| --- | --- | --- | --- |
| 운전면허 all zero | `운전면허번호: 00-00-000000-00` | `DN` 미탐, `BN` 탐지 가능 | DN에서는 제외되지만 일부 숫자 구간이 BN 후보가 될 수 있음 |
| 전화번호 all same | `연락처: 010-0000-0000` | `MN` 탐지 가능 | 반복 숫자 전화번호가 현재 MN 후보로 남을 수 있음 |
| 전화번호 잘못된 prefix | `연락처: 012-1234-5678` | `MN` 미탐, `BN` 탐지 가능 | MN prefix는 실패하나 숫자 구조가 BN 후보가 될 수 있음 |
| 카드번호 Luhn 실패 | `카드번호: 4111-1111-1111-1112` | `CN` 탐지 가능 | Hyperscan 경로에서는 카드 후보가 구조 검증 전 결과에 남을 수 있음 |
| 카드번호 반복 숫자 | `카드번호: 1111-1111-1111-1111` | `CN`/`BN` 탐지 가능 | 반복 숫자도 후보로 남는지 확인 |
| 카드번호 일부 계좌 중첩 | `카드번호: 4111-1111-1111-1111` | `CN` 탐지, `BN` 부분 탐지 가능 | 16자리 카드의 앞 12~14자리 일부가 BN 후보로 잡힐 수 있음 |
| 보고서 번호 | `보고서 번호: 20260210-000123` | `BN` 탐지 가능 | 문맥 필터가 약하면 업무 번호가 BN 후보가 될 수 있음 |

## 기본 룰셋에서 미탐이 정상인 케이스

아래 케이스는 규칙 파일은 있으나 기본 pipeline에 포함되지 않아, 기본 응답에서 나오지 않는 것이 정상이다.

| 구분 | 테스트 문자열 | 기본 기대 결과 | 비고 |
| --- | --- | --- | --- |
| 주소, 도로명 | `서울특별시 강남구 테헤란로 123-4 5층` | 미탐 | `AN` pipeline 제외 |
| 주소, 지번 | `경기도 성남시 분당구 정자동 12-3 번지` | 미탐 | `AN` pipeline 제외 |
| 주소, 도로명 | `인천광역시 연수구 송도과학로 16번길 33` | 미탐 | `AN` pipeline 제외 |
| IPv4 | `접속 IP: 192.168.0.10` | 미탐 | `IP` pipeline 제외 |
| IPv6 | `접속 IP: 2001:0db8:85a3:0000:0000:8a2e:0370:7334` | 미탐 | `IP` pipeline 제외 |

주소나 IP를 실제 응답에 포함해야 하는 테스트라면 `_ruleset.yaml`의 `steps`와 `rule_files`에 `an`, `IP`를 추가하는 별도 룰셋을 만들어 검증해야 한다.

## 문맥 필터 확인 케이스

`default` 룰셋은 `post_context`를 사용한다. 숫자 모양만 맞는 후보라도 주변에 개인정보 라벨이 없거나, `예시`, `샘플`, `테스트` 같은 비개인정보 문맥이 강하면 결과가 제외될 수 있다.

| 구분 | 테스트 문자열 | 기대 결과 | 확인 포인트 |
| --- | --- | --- | --- |
| 라벨 있음 | `계좌번호: 123456-01-123456` | `BN` 탐지 | `계좌번호` 라벨로 문맥 통과 |
| 라벨 있음 | `카드번호: 4111-1111-1111-1111` | `CN` 탐지 | `카드번호` 라벨로 문맥 통과 |
| 라벨 있음 | `여권번호: M12345678` | `PN` 탐지 | `여권번호` 라벨로 문맥 통과 |
| 라벨 없음 | `보고서 번호: 20260210-000123` | 미탐 기대 | 계좌/카드/주민 문맥 없음 |
| 테스트 문맥 | `샘플 카드: 4111-1111-1111-1111` | 제외 가능 | `sample/test` 계열 문맥은 비PII로 볼 수 있음 |
| 반복 행 | `홍길동 010-1111-2222` 다음 줄 `김철수 010-3333-4444` | `MN` 탐지 가능 | 이름+번호 반복 행은 라벨이 약해도 통과 가능 |

### 주민등록번호가 탐지되지 않는 주요 사유

주민등록번호(`SN`)는 단순히 `6자리-7자리` 모양만 맞으면 최종 탐지되는 방식이 아니다. 다음 조건을 순서대로 통과해야 최종 `SN` 결과에 남는다.

1. 형식 매칭: `890512-2054508` 또는 `8905122054508` 같은 주민번호 후보 형식이어야 한다.
2. 체크섬 검증: 기존 부여체계 번호는 마지막 자리까지 주민등록번호 체크섬이 맞아야 한다. 단, 생년월일 기준 2020-10-05 이후 번호는 지역표시번호 폐지/임의번호 부여 체계로 보고 체크섬을 필수 조건으로 보지 않는다.
3. 문맥 통과: `default` 룰셋에서는 주변 문맥이 주민번호로 판단되어야 한다.

따라서 실제 테스트에서 “주민번호처럼 보이는데 안 잡힘”은 아래처럼 구분해서 봐야 한다.

| 원인 | 예시 | 최종 기대 결과 | 상세 사유 |
| --- | --- | --- | --- |
| 체크섬 실패 | `주민등록번호: 900101-1234567` | `SN` 미탐 | 형식은 맞지만 기존 부여체계 체크섬이 맞지 않아 유효 주민번호로 보지 않음 |
| 새 부여체계 | `주민등록번호: 201005-3123456` | `SN` 탐지 가능 | 2020-10-05 이후 생년월일은 임의번호 체계로 보고 체크섬 실패만으로 제외하지 않음 |
| 문맥 부족 | `문서번호 890512-2054508` | `SN` 미탐 가능 | 체크섬은 통과해도 주변 라벨이 `주민등록번호`, `주민번호`, `주번` 등이 아니면 문맥 필터에서 제외될 수 있음 |
| 개인정보 라벨 있음 | `주민등록번호: 890512-2054508` | `SN` 탐지 | 라벨과 번호 형식, 체크섬이 모두 통과 |
| 이름+번호 행 | `홍길동 890512-2054508` | `SN` 탐지 가능 | 이름처럼 보이는 토큰과 번호가 가까이 있으면 `name_pii_row_repeat` 보조 규칙으로 통과 가능 |
| 표 헤더 있음 | `이름\t주민등록번호` 아래 `홍길동\t890512-2054508` | `SN` 탐지 가능 | 셀 값 주변에 라벨이 없어도 같은 열 헤더 또는 반복 행 구조로 통과 가능 |
| 구분자 변형 | `890512 - 2054508`, `890512 2054508` | `SN` | 하이픈 주변 공백 및 6-7자리 공백 구분 지원 |
| 파일 추출 실패 | 이미지로 삽입된 주민번호 | 미탐 가능 | `/pii/detect/file`은 추출된 텍스트 기준으로 탐지하므로 OCR되지 않은 이미지는 텍스트가 없을 수 있음 |

문맥 때문에 제외된 것인지 확인하려면 같은 문장을 `strict` 룰셋과 비교한다. `strict`는 `post_context` 단계가 없으므로, 체크섬과 형식은 통과하지만 문맥만 부족한 후보가 더 많이 나타날 수 있다.

문맥 필터 영향을 배제하고 정규식/구조 검증만 보고 싶으면 `strict` 룰셋으로 비교한다.

```bash
curl -X POST "http://localhost:8005/pii/detect/file" \
  -H "X-PII-RULESET: strict" \
  -F "file=@docs/PII_FILE_TEST_SAMPLE_CONTEXT.docx"
```

## 표 형태 무문맥 탐지 케이스

엑셀, Word 표, CSV, TSV처럼 열 구조가 있는 첨부파일은 각 값 주변에 `연락처`, `계좌번호`, `주민등록번호` 같은 문맥 단어가 반복되지 않을 수 있다. `default` 룰셋은 다음 보조 신호로 일부 표형 데이터를 통과시킨다.

- 상단 헤더: 같은 열 위쪽에 `주민등록번호`, `연락처`, `계좌번호`, `카드번호` 같은 헤더가 있는 경우
- 반복 행: `이름 + 개인정보 값` 형태가 여러 줄 연속 반복되는 경우
- 반복 구조: 같은 타입 후보가 일정한 구조로 연속 등장하는 경우

아래 케이스는 “문장 문맥 없이도 표 구조만으로 탐지되는지”를 확인하기 위한 구간이다.

| 구분 | 테스트 형태 | 기대 응답 키 | 확인 포인트 |
| --- | --- | --- | --- |
| 헤더 있는 TSV | `이름\t주민등록번호\t연락처\t이메일` 아래 값 행 | `SN`, `MN`, `EML` | 셀 자체에는 라벨이 없어도 헤더로 통과 |
| 헤더 있는 계좌 표 | `성명\t은행\t계좌` 아래 값 행 | `BN` | 계좌번호 값 주변 문장 없이 헤더/은행명으로 통과 |
| 헤더 있는 카드 표 | `회원\t카드번호` 아래 값 행 | `CN` | 카드번호 헤더로 통과 |
| 이름+전화 반복 행 | `홍길동 010-1111-2222` 여러 줄 | `MN` | 라벨 없이 반복 행 패턴으로 통과 |
| 이름+주민번호 단일 행 | `홍길동 890512-2054508` | `SN` | SN은 타입별 설정상 이름+번호 1행도 통과 가능 |
| 숫자만 단독 나열 | `123456-01-123456`만 여러 줄 | 탐지 불안정 | 헤더/은행명/라벨이 없으면 문맥 필터에서 제외될 수 있음 |

샘플 파일의 `[F. 표 형태 무문맥 탐지 케이스]` 구간을 확인한다. DOCX에서 실제 Word 표가 아니라 탭/공백 기반 표처럼 추출되더라도, 파일 추출 결과가 줄과 탭을 보존하면 같은 방식으로 검증할 수 있다.

## 문맥 유무 비교 케이스

아래 구간은 동일하거나 유사한 번호가 문맥에 따라 탐지 결과가 달라지는지 확인하기 위한 것이다.

| 구분 | 테스트 문자열 | `default` 기대 결과 | 비교 포인트 |
| --- | --- | --- | --- |
| 주민번호 라벨 있음 | `주민등록번호: 890512-2054508` | `SN` 탐지 | 개인정보 라벨로 문맥 통과 |
| 주민번호 라벨 없음 | `문서번호 890512-2054508` | `SN` 미탐 가능 | 유효한 번호여도 문맥 부족 시 제외 |
| 주민번호 라벨 없음 | `890512-2054508` | `SN` 미탐 가능 | 단독 숫자열은 개인정보 문맥이 없음 |
| 이름+주민번호 | `홍길동 890512-2054508` | `SN` 탐지 가능 | 이름+번호 행 보조 규칙 확인 |
| 계좌 라벨 있음 | `계좌번호: 123456-01-123456` | `BN` 탐지 | 라벨로 문맥 통과 |
| 계좌 라벨 없음 | `123456-01-123456` | `BN` 미탐 또는 불안정 | 번호만 있으면 업무번호와 구분 어려움 |
| 카드 라벨 있음 | `카드번호: 4111-1111-1111-1111` | `CN` 탐지 | 라벨로 문맥 통과 |
| 카드 라벨 없음 | `4111-1111-1111-1111` | 탐지 불안정 | 카드 구조는 맞지만 문맥 없이 오탐 가능성 있음 |

## 결과 확인 방법

응답의 `data`에서 타입별 count를 먼저 확인한다.

예상 응답 구조:

```json
{
  "success": true,
  "data": {
    "sn_cnt": 2,
    "sn": [
      {
        "matchString": "890512-2054508",
        "isValid": true,
        "context_pass": true
      }
    ],
    "eml_cnt": 3,
    "eml": []
  },
  "meta": {
    "ruleset_name": "default"
  }
}
```

확인 기준:

- `*_cnt`가 기대 개수와 맞는지 확인한다.
- `matchString`이 원문과 동일하게 추출됐는지 확인한다.
- `SN`, `CN`, `SSN`처럼 구조 검증이 있는 항목은 무효 샘플이 결과에 없는지 확인한다.
- 주민번호 미탐은 먼저 체크섬 실패인지, 문맥 필터 제외인지, 파일 텍스트 추출 문제인지 구분한다.
- 카드번호와 계좌번호는 중첩 탐지가 발생할 수 있으므로 `CN`과 `BN`을 함께 확인한다.
- `context_pass=false` 또는 `*_ctx_rejected` 류 결과가 보이면 문맥 필터에 의해 제외된 후보인지 확인한다.
- 표 형태 테스트는 `context_accept_by`가 `table_header`, `name_pii_row_repeat`, `repeat_boost` 계열인지 확인한다.
- 주소와 IP는 기본 룰셋에서 미탐이 정상인지 먼저 확인한다.
